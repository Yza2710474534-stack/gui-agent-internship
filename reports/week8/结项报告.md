# 基于屏幕感知与受控执行的桌面 GUI 智能体设计及八周实践研究

## 摘要

针对桌面自动化中界面变化难以处理、操作结果容易被误判以及实验过程缺乏可追溯证据等问题，本项目在八周开发周期内构建了由屏幕采集、文字识别、坐标映射、任务规划、受控执行和结果验证组成的 GUI 智能体原型。项目采用模块化设计，将模型接口与桌面控制分离，通过预览和实时两种运行模式约束实际动作，并以截图、OCR JSON、HTTP 请求及结构化事件日志形成验证链。前期完成了三类公开 GUI 数据的统一处理，历史记录显示共检查3821条数据，其中训练划分3434条、验证划分387条；这一成果属于数据准备，没有进行模型训练。中期建立可限制动作次数、记录失败及重新观察的运行循环，后期增加本地网页控制台、异常提示、窄屏适配和浏览器端到端测试。第八周进一步从前端提交真实实时任务，由项目自身截图、OCR及控制器完成受控页面点击，并以预期结果文字和独立页面状态共同核验。本周自动回归{{AUTO_TESTS}}项通过，既有浏览器场景{{BROWSER_CASES}}项通过，新增专项场景{{LIVE_CASES}}项通过。研究表明，在明确的运行边界内，原型能够形成可审查的单步桌面闭环；同时，现有证据尚不足以证明跨平台通用操作能力、大模型自主长任务能力或真实办公场景总体成功率。

关键词：图形用户界面智能体；屏幕感知；光学字符识别；端到端测试；受控执行；结果验证

## Abstract

This project develops and evaluates a desktop GUI agent prototype over eight weeks. The system separates screen capture, OCR, coordinate mapping, planning, controlled execution and outcome verification. Preview mode avoids desktop actions, while explicitly enabled live mode permits a bounded action. Historical preprocessing records contain 3,821 validated records and a training and validation split, without model training. A local web console submits tasks over HTTP and displays status, logs and screenshots. The final evaluation includes a real live task in which the project controller clicks a visible test button, followed by OCR verification and independent inspection of the target page. The evidence supports a reproducible single action workflow within the tested macOS environment. It does not establish general purpose desktop autonomy or a population level task success rate.

Keywords: GUI agent; OCR; controlled execution; outcome verification; end to end testing

# 第一章 绪论

## 1.1 研究背景与问题提出

桌面软件仍承载着大量信息检索、文档处理、数据录入和跨应用协作任务。完成这些任务时，操作者需要根据当前界面判断控件位置，在多个步骤之间保持任务目标，并在操作后确认软件是否发生了预期变化。传统脚本通常依赖固定坐标、稳定窗口布局或特定应用接口。当界面缩放、窗口移动、网络延迟或提示框出现时，原先有效的脚本可能失效。因此，以自然语言任务为入口、以屏幕观察为反馈的 GUI 智能体具有明确的工程研究价值。

这一方向的困难并不只在于生成一个看似合理的动作。一个完整系统还需要回答当前截图能否代表用户真正看到的界面、识别出的文字是否对应唯一目标、图像坐标能否转换到控制坐标、系统是否具有执行权限，以及操作之后是否达成任务要求。只要其中任一环节缺乏验证，系统就可能在界面没有改变时宣布完成。项目因此将“执行之后如何证明完成”作为与感知和规划同等重要的研究对象，而非把成功解释为程序没有抛出异常。

八周实践还暴露出另一类问题：模块分别能够运行，并不意味着完整产品链路已经成立。模型可以输出步骤，控制函数可以移动鼠标，浏览器可以显示任务状态，但这些能力之间可能依赖人工切换窗口或手动整理证据。结项阶段必须区分模块验证、模拟闭环、人工协助操作与系统自主执行，避免把不同层级的结果合并为一个笼统的成功结论。这一问题直接决定了实验设计及报告组织方式。

## 1.2 研究目标与范围

本项目的主要目标是在现有 Mac 开发环境中实现一个能够被观察、被限制和被复核的桌面 GUI 原型。系统应支持真实屏幕采集与文字定位，提供明确的图像坐标转换方法，允许规划器输出经过校验的结构化动作，保存动作前后的证据，并通过网页入口展示任务状态。研究重点是形成可重复的工程链路，验证各模块在受控条件下的协作关系，为后续更复杂的模型规划和任务执行提供基础。

项目范围包括本地屏幕感知、控制接口、数据规范化、模型适配、实时循环、本地HTTP服务、网页控制台和测试报告。模型训练不属于已经完成的成果；Kaggle上的数据预处理也不能被描述为微调实验。跨平台接口虽然在部分代码中保留，但本次真实操作证据主要来自macOS环境。论文采用这些边界评价成果，研究结论只覆盖实际实现和已保存证据能够支持的范围。

## 1.3 研究方法与主要贡献

研究采用逐层验证的方法。先对截图、坐标和控制参数进行单元测试，再通过依赖注入检查任务循环的控制逻辑，随后使用真实浏览器连接本地服务完成前端到后端的测试，最后在受控可见页面上执行项目控制器动作。各层测试分别回答不同问题：参数是否合法、状态转换是否正确、接口与页面是否连通，以及真实桌面是否发生预期变化。分层后的结果可以相互补充，但不能互相替代。

项目形成的工程贡献主要体现为三方面。其一，建立统一观察记录，使截图、OCR、尺寸和屏幕区域能够关联。其二，将规划和执行之间增加结构校验、运行模式及次数限制，保留动作审查位置。其三，围绕最终结果构建证据链，尤其在第八周将实时成功路径与403拒绝路径分开验收。上述贡献属于原型设计和工程验证，不主张提出新的基础模型或取得公开基准上的领先性能。

# 第二章 相关研究与技术路线

## 2.1 GUI 智能体研究的参考方向

公开研究为项目提供了不同的技术参照。WebArena强调可复现的网页任务环境与功能结果评价[1]；Mind2Web提供来自真实网站的多样任务及操作轨迹[2]。ScreenAgent把桌面交互组织为规划、执行和反思过程[3]；UI TARS研究以截图作为输入的原生GUI交互模型[4]。本项目引用这些工作用于说明研究方向及设计背景，不将其论文结果作为本项目的实验成绩，也未复现其完整训练流程。

在技术路线选择上，本项目没有直接依赖一个模型完成全部工作，而是优先把环境观察、动作参数和执行反馈显式表示出来。这一选择来自实际调试需求：当点击失败时，需要判断原因是文字识别、坐标映射、焦点、权限还是任务完成条件。模块分离有利于缩小问题位置，也便于在模型接口尚未稳定时测试执行器。其代价是规则、状态和数据格式需要保持一致，不能仅凭模型返回的自然语言判断系统已经完成任务。

## 2.2 文字感知与视觉定位的取舍

原型采用EasyOCR提取屏幕文字，将文字、置信度、边界框及中心点作为可检查的定位依据。对于具有明确文字标签的菜单和按钮，这种方法能够提供较直观的解释：目标名称与屏幕识别结果相匹配，再由中心点生成点击坐标。项目也保留图标模板匹配接口，但该接口只验证了有限样本中的匹配流程，不能视为对任意图标的语义理解。文字方法与图标方法的适用范围需要分别描述。

OCR并不能保证目标一定正确。相似字符、菜单小字、遮挡和高分辨率截图都可能影响识别；同一文字也可能同时出现在任务输入框、历史日志和目标软件中。因此，实时点击需要优先选择精确匹配并拒绝无法唯一定位的目标。第八周使用独立目标页与无头控制台，能够降低任务文字进入桌面截图后产生重复匹配的干扰。这种实验布置提高了可重复性，也限制了结论只能覆盖该受控环境。

## 2.3 模型能力与执行能力的分工

项目第三周建立了模拟模型、兼容HTTP API及本地Ollama接口的统一调用方式，并保存了DeepSeek生成浏览器搜索规划的历史结果。该结果证明模型接口可以返回任务步骤，但不证明这些步骤全部由同一系统自动执行。模型输出的合理性与桌面操作的完成性属于两个不同判断。后续实时桥接的单步任务采用明确文字规则定位，避免在最终闭环验收中同时引入模型响应不稳定与桌面环境不稳定两个变量。

这种分工使实验能够回答一个具体问题：当目标和完成条件已经给出，系统能否从网页接收任务、观察真实屏幕、执行一次动作并报告经过核查的结果。该问题比通用自然语言桌面操作范围更窄，但更容易建立完整证据。未来接入模型时，可以复用相同的动作校验和结果验证接口，逐步替换规则规划器，而不必重新设计底层安全约束与证据记录方式。

# 第三章 系统需求与总体设计

## 3.1 功能需求与可验收条件

感知层需要保存实际截图，并记录捕获时间、图像尺寸和原始屏幕区域。OCR层需要输出识别文字与定位信息，且其坐标空间必须与保存的截图一致。执行层需要提供点击、移动、输入、滚动和拖拽等基础函数，同时校验坐标、持续时间和文本范围。任务层需要记录步骤、历史、错误和最终状态。网页层需要能够提交任务、查询进度、展示截图，并在服务异常时给出可采取行动的反馈。

每项功能都需要对应可观察的验收条件。例如，截图成功应有实际文件和有效尺寸；预览成功应产生方案且实际动作数为零；实时成功应有动作日志、后续观察及完成条件；网络失败应有对应请求记录和页面提示。使用这类条件，可以把“页面能打开”与“用户任务已完成”分开。验收标准随系统链路延长而增加，不能继续用早期模块级条件判断后期完整系统。

## 3.2 系统分层与数据流

系统由网页控制台、本地桥接服务、任务执行器、观察适配器、动作控制器和验证器组成。控制台通过POST接口创建任务，通过GET接口轮询任务状态，并请求任务对应截图。桥接服务负责输入验证、运行模式检查和任务并发约束。执行器在后台线程中调用观察和实时循环，将状态变化写回任务存储。验证器检查动作后证据及显式完成条件，最后把结果交还控制台显示。

数据流中有两条互相关联的路径。控制路径描述任务、模式、状态和停止信号如何传播；证据路径描述截图、OCR文件、动作事件及完成判断如何关联。只有控制路径通畅，页面可能显示一个完成状态，却缺少可复核依据。只有证据文件存在，用户又可能不知道其属于哪个任务。因此，每个任务使用独立标识关联前端请求、后端记录和产物目录，使状态与证据能够共同解释一次运行。

## 3.3 预览模式与实时模式

预览模式读取当前屏幕并生成第一条待执行动作，随后停止，不调用桌面执行器。该模式用于检查目标是否能够被识别及动作是否合理，但不能据此宣称真实任务完成。实时模式需要本地服务显式开启，并在动作校验通过后调用控制器。本地网页实时桥接当前主要支持针对可见文字的一次点击；底层循环支持的动作种类更广，并不表示网页入口已经开放相同能力。

两种模式之间的区别贯穿HTTP响应、任务结果和页面说明。未开启实时执行时，服务返回403，其意义是拒绝发生真实动作；开启实时执行后，返回202只表示任务已被接收，仍需等待最终状态。第八周成功实验要求最终结果为done、动作次数为一，并能够找到预期文字。由此，403拒绝、202接收和done完成分别处在不同阶段，不能以其中任一个单独代替完整闭环。

## 3.4 状态管理与可恢复性

任务存储采用锁保护当前任务及记录，避免同时创建多个活动任务。执行期间保留暂停与停止信号，观察、规划和动作前会检查相应状态。停止属于协作式控制，正在进行的OCR调用不会因为网页按钮被按下就立即被强制中断。运行时间限制同样主要在循环边界检查，并非每个阻塞函数的硬实时截止机制。准确说明这些语义，有助于解释用户点击停止之后仍可能需要等待当前阶段结束的现象。

第八周补充了超时与循环上限对应的终止状态，解决其未被识别为终态时可能占住任务槽的问题。前端也增加对应显示，避免后端已经停止而页面仍显示正在处理。状态系统的可靠性不仅依赖成功路径，更依赖所有退出分支能否释放资源、保留错误并恢复后续操作。对于长期运行的桌面工具，这类边界往往比单次动作耗时更直接影响使用体验。

# 第四章 核心模块实现

## 4.1 屏幕采集与坐标映射

截图模块使用MSS读取可用显示器，并保存原始屏幕区域及图像尺寸。若截图经过缩放，坐标转换需要同时考虑比例和区域偏移。设图像宽高为Wi与Hi，对应屏幕区域左上角为L与T，区域宽高为Ws与Hs，则图像点xi与yi映射为xs等于L加xi乘Ws除Wi，ys等于T加yi乘Hs除Hi。该关系只在元数据确实描述执行坐标空间时有效，不能把任意物理像素直接视为鼠标逻辑坐标。

第二周测试构造了多种尺寸与比例，用于检查公式及边界处理。构造数据能够验证运算，却不能替代不同显示器的真实运行。当前机器的实测截图与控制区域均为1470乘956，比例为一比一。项目在历史验收中明确区分了算法尺寸测试和实际显示设备测试。这样的区分避免了把多分辨率单元测试误写成多种物理屏幕都已通过验收。

屏幕权限问题在第四周和第八周都产生过影响。受限进程可能看不到有效显示器，即使截图代码本身没有错误，也会无法生成证据。第五周增加采集探针，无论成功或失败都保存结果摘要。第八周首次检查在受限环境下失败，转入具备桌面会话访问能力的执行环境后，MSS返回有效尺寸并继续实验。处理方式是核对环境与权限，而非使用旧截图冒充当前观察。

## 4.2 OCR观察记录与文字定位

观察适配器把一次采集组织为统一记录，包括图像路径、OCR路径、尺寸、屏幕区域、缩放关系和文字数量。它要求OCR结果的尺寸与截图元数据一致，发现不一致即停止生成观察记录。这样做能够提前阻止最常见的坐标混用问题：识别是在缩放图上完成，点击却直接使用了缩放前的比例。统一记录让调用方不必凭文件名或上下文猜测坐标属于哪个空间。

文字定位先对目标文本进行空白归一化，再检查精确匹配；没有精确结果时才考虑包含关系。匹配结果必须唯一，否则返回停止状态，不任意选择第一项。这一策略降低了重复按钮和日志文字引发误点击的风险，但仍不能消除所有语义歧义。例如，文字中心可能不是可点击区域，页面也可能在识别后发生移动。第八周实验固定了目标页面布局，并专门加入两个同名按钮的拒绝场景，以检验最基本的歧义边界。

## 4.3 动作校验与控制接口

基础控制器封装了鼠标移动、点击、英文输入、滚动和拖拽。校验内容包括有限数值、屏幕范围、合法按键、时间非负及文本字符范围。macOS拖拽使用历史已验证的原生事件路径，并在结束时尝试松开鼠标。输入接口当前限制英文、数字和常用标点，不能把底层存在type_text函数理解成已经支持中文跨应用可靠输入。每个接口的真实验证范围在报告中单独列出。

实时循环将允许动作限制为点击、输入、滚动和等待，并校验动作参数。网页桥接进一步缩小开放范围，拒绝向未知焦点输入文字，实时搜索也不会直接转为任意键盘操作。这种限制保留了可审查性，但会使部分自然语言请求无法执行。对这类请求，返回明确停止原因比猜测焦点并输入更符合当前原型的研究目标。未来扩展应先定义目标控件与结果条件，再开放对应动作。

## 4.4 实时循环与结构化日志

实时循环接收观察、决策、执行、动作验证和最终验证函数，把环境依赖留在调用方。每次动作之前生成规范动作记录，执行之后重新观察并记录验证结果。循环同时保留次数、重试和时间约束。日志以JSONL方式逐条追加，能够定位任务开始、观察完成、动作开始、动作结束及循环完成等事件。即使最终失败，也可以通过最后一条成功事件缩小故障位置。

这种结构便于在不操作真实桌面的情况下测试控制逻辑。单元测试可以注入确定的观察结果、执行反馈或异常，检查系统是否遵守次数限制和失败路径。但注入测试只能说明程序在给定输入下如何转换状态，不能说明实际屏幕内容已经改变。因此，第八周继续保留这些快速测试，同时增加真实前端与真实控制器协作的验证。两者分别保障逻辑稳定性和环境连通性。

## 4.5 完成条件的分层核验

原先的动作后验证主要检查截图与OCR文件存在，最终完成判断主要依据历史记录是否非空。它能够证明系统保存过动作相关证据，却不能证明业务目标已经实现。第八周增加显式结果文本解析，支持在任务中写明“确认出现”及预期文字。动作后从新观察的OCR中查找归一化后的完整文字匹配，最终完成阶段再次核验，缺失预期内容时返回失败，保留对应证据与原因。

对于没有指定预期文字的旧任务，系统仍可保存动作证据，但完成消息明确标注未指定业务完成条件。这是兼容旧接口的处理，并不赋予通用业务验证能力。本次正式成功实验明确给出VERIFIED作为预期结果，且目标页在动作前显示READY，动作后才出现VERIFIED。独立DOM检查同时确认点击次数和页面状态，减少仅依赖单一路径自报成功造成的误判。

# 第五章 八周实施过程与阶段产出

## 5.1 第一周至第二周的基础建设

第一周完成GUI智能体技术调研、Mac开发环境搭建和基础依赖验证，形成研究说明与环境配置文档。项目确定由本地设备负责桌面交互，在需要GPU时使用外部计算环境。依赖验证覆盖截图、OCR和鼠标能力，建立了后续实验所需的最小运行环境。这一阶段最重要的产出是识别系统权限和坐标一致性等先决条件，而非过早追求复杂任务演示。

第二周将零散操作整理为可复用模块，包括全屏与区域截图、连续采集、文字识别、图标定位、坐标还原和结果绘框。历史报告记录了37项单元测试以及真实编辑菜单操作证据。真实菜单展开后的截图能够支持特定点击发生，有限图标样本则只支持模板匹配流程。项目保留这两类证据之间的区别，为后续报告中划分真实运行与模拟测试建立了口径。

## 5.2 第三周的数据与规划接口

第三周统一处理WebArena、ScreenAgent和Mind2Web相关记录，形成一致JSONL格式，并在Kaggle执行预处理检查。历史摘要记录WebArena812条、ScreenAgent2000条、Mind2Web1009条，总计3821条，全部通过当次格式检查；划分后训练部分3434条、验证部分387条。这些数量来自项目导入和处理的数据范围，不能解释为相关公开数据集的完整规模，也不代表已经获得模型训练收益。

同一阶段完成模型调用适配、基础任务Agent、轨迹演示、长任务运行器及任务分类目录。任务目录区分浏览器搜索、打开文件、文本编辑、消息草稿和关闭应用，防止用单一搜索示例概括所有办公流程。历史DeepSeek记录说明接口能够生成六步搜索规划，真实Chrome搜索也有单独证据。但部分步骤之间存在人工切换，其他任务类别主要处于模拟验证阶段，因此报告没有把所有类别写成自动完成。

## 5.3 第四周至第五周的闭环连接

第四周把观察、决策、动作及反馈组织成实时循环，并加入结构化规划、安全动作列表、重试上限和时间约束。专项测试22项及全量回归113项在历史记录中通过。该周真实浏览器搜索由工具观察确认，但项目MSS后端未能保存当次屏幕证据。这个差异促使后续工作把“外部观察看到页面成功”与“项目自身证据链完整”作为两个独立条件检查。

第五周增加屏幕采集健康探针，恢复项目MSS及OCR证据，并建立本地网页到桥接服务的交互。控制台提交任务后收到202，随后轮询任务接口并展示预览结果；未开启实时权限时则返回403。历史搜索结果还通过项目OCR完成条件检查。至此，页面、服务、截图和记录可以关联，但网页实时模式仍未走过成功动作路径，403只能作为安全拒绝证据保留。

## 5.4 第六周至第七周的交互与异常验证

第六周重点完善前端状态反馈、接口信息及截图显示，处理服务未连接、任务完成后状态被健康检查覆盖等问题，并继续保存真实前端请求证据。第七周进一步使用浏览器自动化完成预览成功、403拒绝、请求超时、截图失败、服务断开及恢复等场景。六种视口宽度接受布局测量，最窄320像素页面完成实际预览提交。这些工作使可用性评价从静态页面检查推进到运行状态验证。

第七周的8个浏览器场景及120项自动回归是本次工作的既有基线。超时和截图错误通过网络层注入，服务断开另有实际后端停止实验。报告保留注入位置及运行层级，避免把浏览器收到构造错误响应写成服务真实崩溃。此时最明显的空缺仍是实时成功路径：安全门可以拒绝动作，却没有证据证明打开安全门之后系统能正确执行并返回真实结果。

## 5.5 第八周的收尾与新增成果

第八周针对这一空缺建立独立Chrome目标页，控制台输入明确的点击任务，由本地服务在实时模式下读取屏幕、使用OCR定位目标并调用控制器。目标页面由READY变为VERIFIED，后端动作数为一，最终结果为done；前端同时显示经过核验的完成说明。该实验把输入、HTTP接收、真实屏幕观察、实际动作、结果判断和页面展示连接到同一次任务中，形成了本项目此前缺失的成功证据。

收尾工作还包括预期结果不匹配、同名目标歧义、运行中轮询超时与断线恢复、截图持续不可用及窄屏长任务验证。新增恢复按钮允许用户重新读取同一任务或重新加载截图，避免为了恢复界面而重复创建任务。固定验收入口串联自动测试、原有浏览器测试及显式开启的实时专项，三份Word报告分别承担进度汇报、测试验收和整体研究总结，保持信息层次清晰。

# 第六章 实验设计与评价方法

## 6.1 研究问题与实验对象

实验围绕三个具体问题展开。首先，现有模块在增加完成条件后能否保持回归通过。其次，从真实前端进入实时模式时，系统能否实际执行一次正确动作，并把结果带回页面。最后，当结果不符合预期或观察链路中断时，系统能否停止误报并提供恢复入口。研究对象是当前原型及本机运行环境，采用受控案例验证，不以少量场景推断所有桌面任务的统计表现。

实时目标页只包含清晰的测试按钮和状态文字，操作不涉及发送、删除、付款或修改用户文档。目标页使用可见Chrome窗口，控制台由另一浏览器会话操作。浏览器自动化负责填写控制台任务及检查结果，不直接点击目标按钮。目标按钮的事件计数由页面脚本记录，因此可以独立验证是否有且只有一次真实点击。该设计保留了完整桌面输入链路，同时使预期结果可以明确断言。

## 6.2 分层测试与分类统计

自动回归覆盖基础模块、数据处理、模型接口、任务循环、观察适配、桥接HTTP和新增完成条件。多数测试依赖模拟对象或构造文件，运行速度较快，适合检查边界与异常分支。桥接接口测试虽然会使用真实本地HTTP，也仍然使用测试执行器，不能计入真实桌面成功次数。报告按模块列出数量，再单独列出浏览器和真实环境实验，避免同一用例在多个分类中重复加总。

浏览器回归沿用第七周8个场景，并在本周独立输出目录中重新执行。专项场景增加真实点击及恢复测试。六种宽度作为布局检查维度单列，不与场景数相加。自动测试通过率的分母是测试方法数，浏览器通过率的分母是已定义场景数，而真实业务成功率需要更大、独立采样的任务集合。本报告不把这些分母混在一起，也不将当前通过结果表述为系统整体成功率百分之百。

## 6.3 成功判据与负向对照

正式实时成功案例的任务输入为“点击 VERIFY，确认出现 VERIFIED”。前置条件要求目标页面状态为READY，点击计数为零。验收要求控制台POST返回202，后续任务状态为done，动作数为一，OCR精确匹配VERIFIED，目标页DOM也显示相同结果，前端出现完成说明并加载本次截图。每一条件都针对一个独立的失败可能，组合起来才能支持完整闭环通过。

负向案例使用相同按钮，但将预期文字改为MISSING。实际点击仍会把页面变为VERIFIED，因此动作确实发生，而业务条件应失败。若系统仍返回done，就说明验证器只是检查动作是否执行。另一案例在目标页放置两个VERIFY按钮，要求系统因无法唯一定位而停止，实际点击数保持零。这两个对照分别检验结果语义和目标歧义，比仅复测成功页面更能暴露判断条件过宽的问题。

## 6.4 故障注入与恢复方法

任务轮询超时在浏览器GET请求层注入延迟，使请求超过前端五秒限制；后端继续处理原任务。恢复后从同一任务标识读取结果，检查系统没有重新提交或重复点击。运行中断线使用浏览器网络错误注入，验证页面提示及状态读取恢复。该实验模拟客户端到任务接口不可达，不等同于真实服务进程崩溃，后者由既有浏览器回归中的服务停止与重启场景补充覆盖。

截图不可用通过持续返回404模拟，直至撤去故障后点击“重试截图”。实验要求错误期间页面明确说明图片未加载，恢复后显示本次真实截图，不把旧图当作新证据。320像素场景使用较长任务文案，检查表单按钮是否仍在视口内、文档是否横向溢出以及能否实际提交。此类实验关注操作可达性，不能用仅存在媒体查询规则代替真实浏览器测量。

## 7.3 失败和恢复场景的结果

预期结果不匹配案例实际执行一次点击后返回action_failed，并说明没有观察到MISSING。该结果表明新验证器能够区分动作执行与任务目标达成。重复目标案例返回stopped，动作数为零，符合无法唯一定位时停止的设计。两项结果共同说明系统没有把任意可执行坐标或任意已保存图片直接当作完成依据，但不能证明其他语义条件均已实现自动验证。

轮询超时和连接错误发生后，前端保留原任务标识，显示恢复状态读取入口，并限制重复开始。故障撤去后能够重新查询同一个任务并显示最终状态。截图故障则通过独立重试入口恢复资源加载。恢复的对象分别是任务状态和图像资源，二者没有混为重新执行桌面动作。对于已经被服务进程终止而丢失的内存任务，当前系统仍缺少持久化恢复，本次客户端故障实验不能覆盖这一情况。

## 7.4 实验的有效性与局限

内部有效性方面，独立页面计数、OCR文字及事件记录提供了相互补充的观测，降低单一路径自证成功的风险。受控目标页面布局稳定，也有助于把问题集中在系统链路本身。与此同时，实验未随机化按钮位置、字体、窗口大小或页面语言，样本数量有限，未进行重复采样。因此，本次耗时只能作为该案例的观测值，不能报告为平均延迟、性能分位数或长期可靠性指标。

外部有效性方面，结果来自macOS本机及明确可见的测试页面，不能直接推广到Windows、Linux、多显示器或遮挡窗口。独立测试页没有复杂登录、权限弹窗和动态内容，实际办公软件中的目标识别难度更高。系统实时规划也以规则为主，没有使用模型自主决定多步操作。这些因素限定了论文结论：原型证明受控单步闭环可实现，但距离通用桌面代理仍存在明确研究和工程距离。

# 第八章 产出成果与工程价值

## 8.1 代码与数据成果

两个月内形成了基础感知控制、任务规划与数据处理、实时循环和网页桥接四类代码成果。基础模块提供截图、识别、坐标和控制接口；任务模块提供规范化数据、模型适配、轨迹与任务目录；实时模块组织观察、动作与验证；桥接模块提供本地任务HTTP接口及网页交互。各模块保持相对独立，使后续能够在不重写整个系统的情况下替换OCR、规划器或完成条件。

数据成果包括统一JSONL记录、预处理脚本及历史Kaggle检查摘要。它们降低了不同数据源进入同一实验程序的格式成本，也为将来训练和评估提供了起点。但是，格式通过只说明字段及处理规则符合当前检查，并不代表标注内容绝对正确，也没有证明训练与验证集不存在更高层级的语义关联。后续若进入模型实验，还需要补充划分策略、泄漏检查及独立测试集，不能直接沿用本次工程检查结论。

## 8.2 测试与证据成果

项目保留从第二周模块测试到第八周浏览器与真实环境验证的多层材料。截图和OCR文件帮助复核观察内容，事件日志帮助解释执行过程，HTTP记录帮助确认页面与服务实际通信，报告则将这些材料映射回任务要求。这种组织方式使交付不局限于“代码能跑”的主张，评审者可以从具体案例追踪到请求、动作和最终结果，检查结论是否超出证据范围。

测试分类也是重要产出。过去容易把模拟执行、真实截图、前端自动化和实际桌面动作混在一起，导致报告中的成功含义不明确。本项目逐步建立按模块、层级、检查类型、依赖及证据来源分类的方式。分类使欠缺更容易被识别，例如第七周能明确看出实时成功仍为空缺，从而在第八周针对性补齐。它提高的是评价透明度，不能替代对未覆盖场景的继续实验。

## 8.3 文档与使用体验成果

每周周报与验收测试报告分别交付，前者说明任务完成情况、是否达到预期及后续安排，后者记录用例、证据与边界。结项报告进一步将阶段工作组织为问题、方法、实现、实验和讨论，提供跨周的整体解释。三种文档承担不同职责，避免把周报简单拼接成论文，也避免在验收报告中堆叠无法复现的研究性表述。原始记录仍是实验事实的依据。

网页体验改进包括明确区分预览与实时、展示最近接口、保留任务标识、显示OCR数量和图片加载状态，以及提供错误恢复入口。对于用户而言，系统失败时能否知道当前状态、是否已经执行动作和下一步能做什么，直接影响信任。第八周通过保留原任务并恢复查询，减少了因为界面失联而重复提交的可能。该设计把错误反馈转化为可执行操作，而不仅是一条临时提示。

# 第九章 问题讨论与后续研究

## 9.1 当前方案的主要限制

首先，OCR文字匹配缺乏完整界面语义。即使目标唯一，系统也未必知道该文字属于按钮、说明还是不可交互标签。其次，坐标来自一次观察，在实际点击前窗口可能移动或被其他内容覆盖。第三，运行中的阻塞依赖缺少统一的硬截止机制，时间限制不能保证立刻中断耗时OCR。上述问题均可能在受控演示中不出现，却在日常桌面使用中影响可靠性，应在扩大任务范围之前优先处理。

此外，任务存储位于内存，服务重启后缺少完整任务恢复与证据索引。当前恢复按钮能够处理客户端查询失败，不等于具有崩溃恢复能力。页面对安全检查的展示也主要反映动作规则与模式约束，不能等同于针对任意任务的风险评估。为避免界面指标造成过度理解，后续应更明确地说明每个状态的含义，并将持久化、权限检查及动作前焦点确认纳入下一阶段设计。

## 9.2 扩展为模型驱动任务的条件

将规则规划器替换为模型之前，需要建立稳定的观察输入、动作输出及完成条件接口。模型可以提出操作，但不能直接跳过参数验证或自行决定已完成。对于多步任务，完成条件应由独立验证逻辑表达，例如目标文件是否存在、草稿是否保存或指定页面是否出现。验证器可以使用OCR、应用状态及可访问性信息组合判断，但应记录每种信息来源及其失败边界，防止再次回到单纯相信模型叙述的方式。

多步能力还需要处理状态积累与错误传播。一次点击成功并不能保证后续输入的焦点正确，也不能保证重复尝试没有副作用。下一阶段应从少量固定工作流出发，定义每步前置条件、可重试动作和不可重复动作，再逐步引入模型选择。消息发送、删除等不可逆操作应保持人工确认。研究评价则需要记录人工接管次数，而非把人工修正后的最终完成全部计入系统自主成功。

## 9.3 更严格的实验设计

为了估计真实任务成功率，需要建立独立任务集合，覆盖不同应用、语言、窗口尺寸和干扰条件，并进行多次运行。测试集应在开发阶段尽量隔离，避免只针对已知页面调参。除了完成率，还可以测量误点击、重复动作、恢复成功率、人工干预、端到端耗时及证据缺失比例。指标需要说明样本数和统计口径；当前单次成功案例只能作为机制验证，不能替代这类系统性评估。

性能优化也应基于测量。当前循环多次执行完整屏幕OCR，耗时可能主要来自识别而非HTTP或点击。未来可以分段记录采集、检测、识别、规划、执行和验证时间，识别真正的瓶颈，再评估区域裁剪、缓存或轻量模型。优化后必须重新验证坐标和完成条件，因为缩小观察范围可能遗漏关键弹窗。任何速度提升都应与任务正确性一起报告，避免只展示更短耗时而牺牲可靠性。

## 9.4 数据与交付的持续维护

后续交付应继续保留源码、运行入口、环境说明和证据清单，并对截图中的无关个人信息控制访问范围。历史绝对路径只能作为当时环境记录，复现时应生成新目录。OCR模型权重和虚拟环境不适合不加说明地混入代码包，接收者需要知道如何准备依赖及首次运行时间。固定验收入口能够减少手工遗漏，但执行真实桌面动作仍应显式开启，并在受控页面上进行。

论文式报告也需要随实验变化维护。如果未来增加了模型训练，就应补充训练配置、数据划分、消融实验和资源消耗；如果增加了跨平台支持，就应提供对应真机证据。当前报告对这些内容只提出后续研究条件，没有把计划当成成果。保持这种边界，有助于让研究总结成为可以继续工作的技术依据，而非一次性的完成证明。

# 第十章 结论

本项目在八周内完成了桌面GUI原型从环境准备、模块封装、数据处理和模型接口，到实时循环、本地网页控制台及分层验收的连续建设。阶段成果包含可复用代码、统一数据记录、结构化日志、浏览器测试脚本和独立周报。第八周通过真实前端输入、真实MSS观察、EasyOCR定位和项目控制器点击，取得一次带有业务结果复核的实时成功闭环，解决了此前只验证403拒绝而缺少成功执行证据的问题。

研究结果支持两个工程判断。其一，将感知、规划、执行与验证分离，有助于定位系统问题并保留替换接口。其二，完成状态必须与明确结果条件和同次运行证据关联，文件存在或动作返回不能单独证明任务完成。负向条件、重复目标和恢复实验进一步说明，可靠性需要同时检查成功、拒绝与中断路径。当前成果可作为后续扩展的基础，但尚未证明通用桌面自主操作、跨平台可靠性或模型训练收益。

下一阶段应优先完善动作前焦点与窗口校验、任务持久化、阻塞调用取消，以及更广泛的独立任务测试，再逐步接入模型驱动多步规划。结项并不意味着所有研究问题已经解决，而是明确现有系统能做什么、这些判断由什么证据支持，以及继续扩大能力需要满足哪些条件。以可复核的工程成果为基础推进后续研究，能够降低演示效果与真实使用之间的落差。
